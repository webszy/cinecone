4.3异常三态 ⑦（每次失败都要有结尾）

三种异常的处理原则

竞品的共同点是「失败时不说话」——用户只能自己猜，猜的结果就是 1 星。

① 广告无填充 → 告知原因 + 可重试（不发币）静默失败仍是骗，但无广告凭证就发钱等于给刷子开门。明确提示 + 一键重试，信任靠「不装死」，不靠补偿币。
② 提现被拒 → 原因 + 退回 + 申诉原因从固定枚举出（信息不符 / 风控复核 / 渠道失败），余额原路退回，48h 内给答复。
③ 开屏超时 → 8s 硬进首页兜底写在客户端，不读服务端配置。这一条缺失就是 CoinDrama / Spark 的黑屏死锁事故。
统一原则任何一个按钮点下去，必须有可见结果：跳转、Toast、或状态变化。三选一，不允许「没反应」。

这三屏决定「首次提现能不能一次过」。竞品把登录放在首屏之前、把收款信息放在提现失败之后，两个顺序都是错的。

5.11 广告与提现的边界（解耦契约）

广告是币的唯一入口，提现是币的唯一出口。两者共用账本，但不共用代码路径、不共用故障面、不互相同步调用。本节把这条边界写成可校验的契约：广告侧任何异常都不得让提现失败或变慢，提现侧任何变更都不得改变广告投放与发币。

唯一合法的数据流（单向）

广告播放 → ad_events（S2S 验签）→ Ledger 追加 AD_REWARD → available_balance → POST /v1/withdraw → 提现状态机 → 打款

箭头只能向右。提现域不得读 ad_events 或广告配置；广告域不得同步调用提现接口。跨域信息只允许通过下面的事件异步传播，且任何一方都不得因为对方的故障而阻塞自己。

数据所有权：谁能写、谁只能读

数据归属读写规则
ad_events / ad_unit 配置 / 频控计数广告域只有广告服务写。提现域不可见，也不参与任何提现判定
ledger（金币账本）账本域（独立服务）广告、任务、签到、提现都只能调 Ledger API 追加（AD_REWARD / TASK / WITHDRAW_HOLD / WITHDRAW_REFUND / REVERSAL），任何一方都不得直接 UPDATE 余额；查询对所有域只读
withdraw_order 与状态机提现域只有提现服务写。广告域不得同步查询；需要感知到账时只消费 withdrawal.paid 事件

5.16 进度条与增长动效约束

这一节解决一个具体冲突：产品要「前面涨得快、后面涨得慢，永远差一点」，红线要「进度不能说谎」。两者不是不能共存——可以给手感，不能给假终点。

进度条：分段缓动 + 末端锚定

// p = 展示进度（0–1），b = available_balance / 门槛（真实比例） seg(p) = p < 0.40 ? p / 1.6 // 前段快：1 元额度走 1.6 元进度 : p < 0.75 ? 0.25 + (p-0.40) // 中段线性 : 0.60 + (p-0.75)*0.45 // 末端锚定：达标必须 100%，永不出现「99% 但能提」 display = (b >= 1.0) ? 1.0 : min(seg(b), 0.99) label = "Faltam {ceil((1-b) * 单集进度)} episódios" // 只讲集数，不讲百分比

三条不可协商：① display 随 b 单调不减，任何情况下不许回退（冲正导致余额下降时，进度条先停在原位 3s 再回落一次，且只落一次）；② b ≥ 1 时 display = 1.0 且按钮变绿——这就是红线 14 的判定点；③ 界面不出现百分比数字，只出现「还差 N 集」，避免把缓动系数解读成承诺。

关于「永远到不了 100%」：这句话在工程上只能有两种实现——A 让门槛永远达不到（等于不发钱，直接违反红线 1，且是竞品被投诉最狠的点）；B 门槛可达但视觉上后期变慢（本节的实现）。本案只能走 B，并且达标瞬间必须给 100% 与可提状态。如果坚持 A，就不是产品问题而是合规问题：Play 的欺骗性行为条款与巴西 CDC 都覆盖「虚假收益承诺」。该冲突已登记为 OPEN-14，结论未定前按 B 实现。

Offerwall（原 MZ-09-01 / 02）本期不做 首发要解决的是「首提可信」而不是「多一条收入线」：任务墙会把首次到账路径拉长，客服口径从「提现为什么不到」扩成「任务为什么不结算」；CPA 任务源质量不可控，贷款 / 加密 / 假 PayPal 是竞品投诉重灾区，人工审核成本高于分成收入 ① D30 留存与首提率达标，且客诉已收敛到提现类；② 找到可白名单化的游戏试玩源，且能做到 T+1 结算率 ≥95%、失败可申诉有客服；③ 有独立审核人力（≥0.5 人）
订阅与内购（原 MZ-08 全 8 条）砍掉 不做内容付费墙的前提下，「付费」只能卖「去广告 + 加速」，而核心人群是来赚币的免费用户——六款竞品零订阅不是没人想到，是转化不起来；同时要背 RTDN、退款撤单、恢复购买、地区定价、审核合规一整套固定成本，收入却是高方差的小比例。首发的验证目标是「首提能否达成」，多一条付费线只会分散资源与客服口径 ① 免费侧 D30 留存与 ARPDAU 已稳定、广告收入见顶；② 有明确证据表明存在愿付费的去广告人群（如「因广告退出」占比 >3% 且集中在高活跃用户）；③ 能承担 Billing 的长期维护人力（≥1 人，含每月审核与退款处理）
竞品互导（原 MZ-09-04）不做，默认「不开放」 把买量买来的用户再导给同行；LTV 没算清之前做，等于自己削 ARPDAU 单用户 LTV 与 CAC 差值稳定为正，且能算清「导走 1 个用户换回多少」的净收益
单剧解锁（原 MZ-08-01 的 unlock_drama）砍掉 单剧解锁本质是「花 R$9,99 免一部剧的广告」，与「看广告赚币」的核心循环直接对立：愿意付的人不看了，不愿付的人本来也看；且解锁态要在频控、素材、账本三处开洞，复杂度接近订阅 与订阅一并重启（同一套 Billing 能力），不单独评估
第三方 CPA / 联盟任务不做 与 Offerwall 同因：结算不可控 + 类目风险；且会给「金币来自哪里」的口径添第三条来源 同 Offerwall 的第 ② 条
iOS 端不做（2026-11-08 已定） 见 6.4「OPEN-08 已关闭」：只做 Android 单端，开发语言 Kotlin Android 端 D30 与净 ARPDAU 双双达标，且有第二端维护人力
和「P2 观察项」的区别，别混着说：P2 仍在范围内、有编号、只是等数据（如 BF-04-07 双倍时段）；本节的东西没有编号、不进统计、不进任何排期表。把两者混在一起数，总数就会又对不上。
为什么现在写下这条：六款竞品里有四款上过 Offerwall 或互导，其中三款的投诉集中在「任务做了不结算」与「装完被跳转到贷款 App」。这两类差评对「能不能真提现」的信任伤害，比多一条收入线的收益大得多。
